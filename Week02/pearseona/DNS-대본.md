DNS라는 용어가 낯설더라도, 웹사이트나 앱을 사용할 때 이미 여러 번 이용하고 계셨을 텐데요.

DNS는 개발 직군의 기술 면접에서도 자주 다뤄지고, 우리가 인터넷을 사용하는 과정에서도 빠질 수 없는 기술이기 때문에 오늘 발표 집중해서 들어주시면 감사하겠습니다.

오늘은 DNS가 왜 필요한지, 그리고 우리가 입력한 주소가 어떻게 실제 서버까지 연결되는지 쉽고 간단하게 알아보겠습니다.

## Slide3 - 도메인 이름의 필요성

먼저 도메인 이름과 IP 주소가 무엇인지 간단히 알아보겠습니다.

도메인 이름은 `naver.com`, `youtube.com`처럼 사용자가 웹사이트에 접속하기 위해 입력하는 문자 주소입니다.

반면 IP 주소는 컴퓨터가 인터넷에서 목적지 서버를 찾아갈 때 사용하는 숫자 주소입니다.

여러분 중에 네이버나 유튜브의 실제 IP주소를 외우고 계신 분 있으실까요?

아마 거의 없으실 거라고 생각되는데요. 숫자로 된 IP 주소는 사람이 기억하기 어렵기 때문에, 우리는 의미가 있고 기억하기 쉬운 도메인 이름을 사용합니다.

쉽게 비유하면 도메인은 우리가 기억하는 장소의 이름이고, IP 주소는 컴퓨터가 목적지를 찾아갈 때 사용하는 주소입니다.

참고로 하나의 서비스가 반드시 하나의 IP 주소만 사용하는 것이 아니라, 접속한 위치나 서비스 상태에 따라 서로 다른 IP 주소가 사용되기도 합니다.

---

## Slide4 - DNS의 역할

이렇게 도메인 이름과 IP주소 사이를 연결해주는 것이 바로 DNS입니다.

DNS는 `Domain Name System`의 약자로, 도메인 이름과 관련된 정보를 찾아주는 인터넷의 주소 안내 시스템입니다.

웹사이트에 접속할 때는 주로 도메인 이름과 연결된 IP 주소를 찾아줍니다.

예를 들어 사용자가 코테이토 사이트의 주소인 `www.cotato.com`을 입력하면 DNS가 이 이름과 연결된 서버의 IP 주소를 찾아주고, 

그 다음 브라우저가 해당 IP 주소를 이용해 실제 서버에 연결합니다.

DNS가 직접 웹사이트의 데이터를 보내주는 것은 아니고, 브라우저가 어느 서버로 가야 하는지 알려주는 역할을 한다고 이해하시면 됩니다.

---

## Slide5 - 도메인의 계층 구조

도메인은 하나의 긴 이름처럼 보이지만, 실제로는 점을 기준으로 여러 단계로 나뉘는데요.

`www.cotato.com`을 오른쪽부터 살펴보겠습니다.

가장 오른쪽의 `.com`은 최상위 도메인으로, 인터넷 주소의 큰 분류라고 생각하시면 됩니다.

그다음 `cotato`는 직접 등록해서 사용하는 이름이고, 맨 앞의 `www`는 그 안에서 서비스를 구분하는 서브도메인입니다.

DNS의 계층은 오른쪽으로 갈수록 큰 범위를 나타냅니다. 

ㅣ실제 조회에서도 큰 범위에서 시작해 `.com`, `cotato.com`, `www.cotato.com`처럼 담당 범위를 점점 좁혀갑니다.

따라서 우리가 주소를 읽을 때는 왼쪽부터 읽지만, DNS의 계층 구조를 이해할 때는 오른쪽부터 살펴보면 편합니다.

## Slide6 - URL과 도메인의 차이

지금까지 살펴본 도메인과 URL은 비슷해 보이지만 , 나타내는 범위가 다른데요.

먼저 URL은 인터넷에서 원하는 자원의 위치를 나타내는 전체 주소입니다. 

화면에 있는 이 예시는 코테이토 홈페이지에서 제가 13기에 참여했던 도트폴리오 프로젝트로 이동하는 URL인데요. 이 주소를 예시로 살펴보겠습니다.

가운데 파란색으로 표시된 `www.cotato.com`이 도메인으로, 어느 서버로 갈지를 나타내는 핵심 이름입니다. 

URL은 여기에 통신 방식인 `https`와 서버 안에서 찾을 구체적인 위치인 `/project/49`까지 포함합니다.

비유하면 도메인이 건물의 주소라면, URL은 그 건물의 몇 층, 어느 방으로 갈지까지 포함한 상세 주소입니다.

즉, 도메인은 URL을 구성하는 한 부분이라고 볼 수 있습니다.

## Slide7 - 웹사이트 접속 단계

그렇다면 주소창에 URL을 입력한 뒤 화면이 나타날 때까지 어떤 일이 일어날까요?

먼저 브라우저가 URL에서 도메인 이름을 확인합니다.

그다음 DNS를 통해 도메인과 연결된 IP 주소를 찾고, 해당 주소의 서버에 연결합니다.

서버에 연결하고 필요한 데이터를 요청하면 서버가 데이터를 보내주고,

 마지막으로 브라우저가 그 데이터를 바탕으로 우리가 보는 화면을 만들어줍니다.

우리는 주소를 입력하고 엔터를 누르면 바로 접속된다고 느끼지만, 그 짧은 순간에 이런 단계들이 빠르게 진행됩니다.

이 중에서 오늘 자세히 살펴볼 부분은 두 번째인 DNS 조회 과정입니다.

## Slide8 - 저장된 주소의 확인 순서

DNS 조회를 할 때 컴퓨터는 인터넷에 있는 DNS 서버에 매번 처음부터 질문하지 않습니다.

먼저 브라우저와 운영체제의 DNS 캐시처럼 가까운 곳에 이미 저장된 주소가 있는지 확인합니다.

컴퓨터에 직접 주소를 지정한 `hosts` 파일의 정보가 사용되는 경우도 있습니다.

정확한 확인 순서는 브라우저나 운영체제에 따라 달라질 수 있지만, 핵심은 이미 알고 있는 주소가 있다면 그것을 먼저 사용한다는 점입니다.

가까운 곳에서도 주소를 찾지 못했을 때 DNS 리졸버에게 질문합니다.

그렇다면 이렇게 저장된 주소는 얼마나 오래 사용할 수 있을까요?

---

## Slide9 - 저장된 주소의 사용 기한

이렇게 한 번 찾아둔 주소를 무한정 사용하지는 않습니다.

DNS 정보에는 TTL, 즉 `Time To Live`라는 유효기간이 설정되어 있는데요.

화면의 예시처럼 예를 들어 TTL이 5분이라면, DNS에서 찾은 주소를 아까 봤던 브라우저 캐시나 OS 캐시에 저장한 뒤 딱 5분 동안만 재사용할 수 있습니다.

덕분에 같은 사이트에 접속할 때마다 DNS 조회를 처음부터 반복하지 않아도 되기 때문에 접속이 더 빨라지고, DNS 서버의 부담도 줄어듭니다.

그리고 TTL이 만료되면 해당 캐시를 더 이상 유효한 정보로 사용할 수 없게 되고,  이후 그 주소가 다시 필요해지면 DNS 조회를 새로 진행합니다.

즉, 주소를 조회하고, TTL 동안 재사용하고, TTL이 만료된 다음 요청에서 다시 조회하는 과정이 반복됩니다.

---

## Slide10 - DNS 리졸버의 역할

근데 만약 내 컴퓨터에 사용할 수 있는 주소가 없다면 인터넷에 질문해야 하는데요.

그렇다고 내 컴퓨터가 전 세계의 DNS 서버를 직접 찾아다니는 것은 아닙니다.

이때 DNS 리졸버라는 도우미에게 대신 주소 찾기를 부탁합니다.

내 컴퓨터가 'www.cotato.com의 IP 주소가 뭐야?'라고 질문하면, 리졸버는 '내가 대신 찾아올게' 하고 필요한 DNS 서버들을 대신 방문해 답을 찾아옵니다.

DNS 리졸버는 보통 인터넷 통신사나 회사, 또는 외부 DNS 서비스에서 제공합니다.

즉, DNS 리졸버는 사용자와 여러 DNS 서버 사이에서 주소를 대신 찾아주는 중개자입니다.

---

## Slide11 - 리졸버가 방문하는 세 가지 서버

그렇다면 리졸버는 어디를 방문할까요?

크게 세 종류의 DNS 서버를 차례로 확인합니다.

첫 번째는 시작점 역할을 하는 루트 DNS 이고,  루트 서버는 `.com`을 담당하는 서버가 어디에 있는지 안내합니다.

두 번째는 TLD DNS 서버입니다. TLD는 `Top-Level Domain`의 약자로, 여기서는 `.com` 도메인들을 관리하는 안내소라고 생각하면 됩니다.

TLD 서버는 `cotato.com`을 담당하는 DNS 서버가 어디인지 알려줍니다.

마지막은 권한 DNS 서버입니다. 권한 DNS 서버에는 해당 도메인에 대해 최종적으로 관리되는 DNS 정보가 저장되어 있습니다.

앞의 서버들이 다음에 찾아갈 곳을 안내한다면, 권한 DNS 서버는 도메인에 설정된 최종 정보를 알려주는 구조입니다.

---

## Slide12 - DNS 조회의 전체 과정

이제 지금까지의 과정을 하나로 연결해 보겠습니다.

사용자가 리졸버에게 주소를 찾아달라고 요청하면, 리졸버가 본격적인 탐색을 시작하게 되는데요.

먼저 시작점인 루트 DNS 서버에 `.com` 담당 서버의 위치를 묻습니다.

그다음 안내받은 `.com` TLD 서버에 `cotato.com`을 담당하는 서버가 어디인지 질문합니다.

마지막으로 권한 DNS 서버에 `www.cotato.com`의 주소를 물어보고, 여기서는 `203.0.113.10`이라는 예시 IP 주소를 받았다고 가정하겠습니다.

리졸버는 이렇게 찾아온 IP 주소를 사용자에게 전달하고, 사용자 쪽에서도 일정 시간 캐시에 저장합니다.

이것이 도메인 이름으로 IP 주소를 찾는 DNS 조회의 전체 흐름입니다.

---

## Slide13 - DNS의 두 가지 질문 방식

방금 살펴본 DNS 조회 과정에는 두 가지 질문 방식이 사용됩니다.

먼저 왼족의 사용자와 리졸버 사이를 보면, 사용자가 “찾아가는 과정은 맡길 테니 최종 답을 알려줘”라고 요청합니다.

이처럼 요청을 받은 쪽이 최종 결과까지 책임지고 찾아주는 방식을 재귀적 질의라고 합니다.

반면 오른쪽 리졸버와 루트, TLD, 권한 DNS 서버 사이를 보면, 리졸버는 각 서버에게 "답이 없다면 다음 담당자를 알려줘"라고 질문하면서 한 단계씩 찾아갑니다.

이를 반복적 질의라고 합니다.

정리하면 사용자는 리졸버에게 최종 답을 요청하고, 리졸버는 담당 서버들을 차례대로 방문하며 답을 찾아옵니다.

## Slide14 - DNS 레코드의 종류

이번에는 DNS 서버에 어떤 정보가 저장되어 있는지 살펴보겠습니다.

DNS 레코드는 도메인에 어떤 정보를 연결할지 정해놓은 설정입니다.

여기 표를 보시면 종류가 여러 개 있지만 모두 외우실 필요는 없습니다.

A 레코드는 도메인을 IPv4 주소에 연결하고, AAAA 레코드는 IPv6 주소에 연결합니다.

CNAME은 하나의 도메인 이름을 다른 도메인 이름에 연결합니다.

MX는 이메일을 받을 서버를 지정하고, TXT는 도메인 소유권 확인이나 보안 설정 등에 사용하는 문자 정보를 저장합니다.

이 중 붉은색으로 표시되어 있는, 웹 서비스를 구성할 때 자주 접하게 되는 A 레코드와 CNAME의 차이를 조금 더 살펴보겠습니다.

---

## Slide15 - A 레코드와 CNAME

A 레코드와 CNAME의 차이는 연결되는 대상을 보면 쉽게 이해할 수 있습니다.

왼쪽의 A 레코드는 `api.cotato.com`이라는 이름에 `203.0.113.10`과 같은 IP 주소를 직접 연결합니다.

즉, 이름에서 IP 주소로 바로 이동하는 방식입니다.

오른쪽의 CNAME은 `www.cotato.com`을 IP 주소가 아닌 `service.host.com`이라는 다른 도메인 이름에 연결합니다.

따라서 CNAME을 조회한 경우에는 연결된 도메인 이름의 IP 주소를 추가로 찾아야 합니다.

정리하면 A 레코드는 IP 주소에 직접 연결하고, CNAME은 다른 이름을 거쳐 연결합니다.

---

## Slide16 - 서브도메인의 역할

도메인을 하나만 가지고 있어도 앞에 붙는 서브도메인을 활용해 목적에 따라 서비스를 구분할 수 있는데요.

예를 들어 `www`는 일반 사용자를 위한 웹사이트, `admin`은 관리자용 서비스, `api`는 백엔드 통신, `static`은 이미지나 정적 파일을 제공하는 용도로 사용할 수 있습니다.

각 서브도메인은 필요에 따라 같은 서버를 가리킬 수도 있고, 서로 다른 서버를 가리킬 수도 있습니다.

이렇게 서브도메인으로 서비스를 구분하면 하나의 도메인 아래에서도 여러 서비스를 목적에 맞게 구성하고 운영할 수 있습니다.

## Slide17 - DNS와 CDN

다음은 웹사이트 속도를 높여주는 DNS와 CDN의 관계입니다.

CDN이란 콘텐츠를 여러 지역의 서버에 나누어 저장하고, 사용자에게 빠르게 전달하는 시스템입니다. 

쉽게 말하면 자주 사용하는 콘텐츠를 여러 지역의 지점 서버에 복사해 두는 것입니다.

CDN과 연결된 DNS는 사용자의 네트워크 위치와 서버의 상태 등을 고려해 적절한 CDN 서버의 주소를 응답할 수 있습니다.

화면에서는 이해를 돕기 위해 서울 사용자를 서울 서버로, 부산 사용자를 부산 서버로 안내하는 모습으로 단순하게 표현했는데요.

실제로는 반드시 물리적으로 가장 가까운 서버만 선택하는 것은 아니고, 네트워크 상태나 서버 부하 등도 함께 고려될 수 있습니다.

이런 방식으로 사용자는 비교적 가까우면서 상태가 좋은 서버에서 콘텐츠를 받아 더 빠르게 서비스를 이용할 수 있습니다.

## Slide18 - DNS 변경의 전파 시간

그런데 서버의 IP 주소를 변경해도 모든 사용자가 즉시 새로운 주소로 접속하는 것은 아닙니다.

왜냐하면 앞에서 살펴본 TTL과 캐시 때문입니다.

기존 IP 주소의 TTL이 아직 남아 있는 캐시는 이전 주소를 계속 사용할 수 있습니다. 반면 TTL이 만료되어 DNS를 다시 조회한 곳에서는 새로운 주소를 받게 됩니다.

각 캐시는 서로 다른 시점에 기존 주소를 저장했기 때문에 새 주소가 적용되는 시점도 서로 다를 수 있습니다.

흔히 이를 DNS 전파 시간이라고 부르는데요. 새로운 정보가 전 세계로 천천히 이동한다기보다, 여러 곳에 남아 있는 기존 캐시가 차례대로 만료되는 과정에 가깝습니다.

그래서 서버 주소를 변경할 계획이 있다면 변경 전에 TTL을 미리 낮춰두기도 합니다.

## Slide19 - DNS 장애의 원인

그렇다면 DNS에 문제가 생기면 어떤 일이 발생할까요?

잘못된 DNS 레코드, 도메인 만료, DNS 제공자의 장애 등으로 주소를 정상적으로 찾지 못할 수 있습니다.

DNS를 변경한 직후에는 일부 캐시에 이전 주소가 남아 있어 특정 사용자만 접속에 실패하는 경우도 있습니다.

이때 실제 애플리케이션 서버는 정상적으로 실행되고 있어도 사용자는 서버의 위치를 찾지 못해 사이트에 접속할 수 없습니다.

브라우저에서 볼 수 있는 “사이트에 연결할 수 없음” 또는 “서버 IP 주소를 찾을 수 없습니다”와 같은 메시지가 DNS 문제로 발생하기도 합니다.

즉, DNS는 사용자가 서버로 가기 위한 길 안내 역할을 하기 때문에, DNS 조회에 문제가 생기면 서버가 정상이어도 사용자가 서비스에 도달하지 못할 수 있습니다.

## Slide20 - 교육 목표 돌아보기

발표 시작할 때 말씀 드렸던 세가지 교육 목표 다들 기억나시나요? (곧 마무리라고 언급)

세 가지 교육 목표를 다시 확인해 보면서 마무리하겠습니다.

첫째, DNS가 필요한 이유는 복잡한 숫자 IP 주소 대신 사람이 기억하기 쉬운 이름을 사용해 인터넷 서비스에 접근하기 위해서였습니다.

둘째, 도메인 이름으로 IP 주소를 찾을 때는 먼저 캐시와 같이 가까운 곳의 정보를 확인합니다. 주소가 없다면 리졸버가 루트, TLD, 권한 DNS 서버를 차례대로 찾아가 최종 정보를 받아옵니다.

셋째, DNS와 CDN을 활용하면 사용자를 적절한 서버로 안내해 빠르게 콘텐츠를 제공할 수 있습니다.

반면 DNS를 변경하면 기존 캐시의 TTL이 만료될 때까지 반영 시간이 필요하고, DNS에 장애가 발생하면 서버가 정상이어도 사용자가 서비스에 접속하지 못할 수 있습니다.

오늘 함께 나눈 내용이 앞으로 인터넷이나 웹 서비스를 이용하고 개발하실 때, '보이지 않는 곳에서 이런 일이 일어나고 있었구나' 하고 조금 더 친숙하게 와닿는 계기가 되었으면 좋겠습니다.

감사합니다.
