# DNS 공부자료

---

## 1. DNS란?

DNS는 **Domain Name System**의 약자다. 도메인 이름에 연결된 IP 주소와 여러 정보를 찾아주는 시스템이다.

사용자가 브라우저에 `www.cotato.com`을 입력하면 DNS가 해당 이름에 연결된 IP 주소를 찾는다. 브라우저는 그 IP 주소를 이용해 실제 웹 서버에 접속한다.

DNS는 전화번호부와 비슷하다.

| 전화번호부 | DNS |
| --- | --- |
| 사람의 이름 | 도메인 이름 |
| 전화번호 | IP 주소 |
| 이름으로 전화번호 검색 | 도메인으로 IP 주소 검색 |

DNS가 웹페이지 자체를 전달하는 것은 아니다. 브라우저가 접속해야 할 서버의 주소를 알려주는 역할을 한다. 실제 웹페이지 데이터는 DNS 조회 이후 웹 서버가 전달한다.

---

## 2. 도메인의 계층 구조

도메인은 하나의 이름처럼 보이지만 점을 기준으로 여러 단계로 나뉜다.

```
www.cotato.com
│      │     └─ 최상위 도메인(TLD)
│      └────── 등록한 도메인 이름
└───────────── 서브도메인
```

### 최상위 도메인

도메인에서 가장 오른쪽에 있는 부분이다. TLD는 **Top-Level Domain**의 약자이며 `.com`, `.org`, `.net`, `.kr` 등이 해당한다.

### 등록한 도메인 이름

`cotato.com`에서 `cotato`에 해당하는 부분이다. 일반적으로 도메인 등록 기관을 통해 등록해서 사용하는 이름이다.

### 서브도메인

등록한 도메인 앞에 추가하는 이름이다. `www`, `api`, `admin`처럼 서비스의 역할을 구분할 때 사용할 수 있다.

DNS의 계층은 오른쪽의 큰 범위에서 왼쪽의 구체적인 범위로 이어진다.

---

## 3. URL과 도메인의 차이

도메인은 URL을 구성하는 요소 중 하나다.

```
https://www.cotato.com/project/49
└─┬─┘   └────┬─────┘└───┬────┘
통신 방식       도메인        경로
```

- `https`: 브라우저와 서버가 통신할 때 사용하는 방식
- `www.cotato.com`: 연결할 서버를 나타내는 도메인
- `/project/49`: 서버에서 요청하는 자원의 경로

도메인을 건물의 주소라고 생각하면 URL은 건물 안의 구체적인 위치까지 포함한 상세 주소라고 볼 수 있다.

예를 들어 `www.cotato.com`은 코테이토 웹사이트를 나타내는 도메인이다. 여기에 `/project/49`를 붙이면 웹사이트 안의 특정 프로젝트 페이지를 나타내는 URL이 된다.

---

## 4. 웹사이트 접속 과정

사용자가 브라우저에 URL을 입력하면 다음 과정이 진행된다.

```
URL 입력
   ↓
DNS로 IP 주소 확인
   ↓
해당 서버에 연결
   ↓
데이터 요청과 응답
   ↓
브라우저가 화면 표시
```

먼저 DNS를 통해 도메인에 연결된 IP 주소를 찾는다. IP 주소를 알아내면 브라우저는 해당 서버에 연결하고 필요한 데이터를 요청한다.

서버가 HTML, CSS, 이미지 등의 데이터를 보내면 브라우저가 이를 조합해 화면으로 보여준다.

실제로는 HTTPS 연결과 인증서 확인 등 더 많은 과정이 있지만, 이 자료에서는 DNS 조회를 중심으로 단순화한다.

---

## 5. DNS 캐시와 확인 순서

브라우저와 컴퓨터는 이전에 찾은 DNS 응답을 일정 시간 저장한다. 이렇게 임시로 저장한 데이터를 **DNS 캐시**라고 한다.

주소가 필요할 때마다 외부 DNS 서버에 질문하면 시간이 더 걸리고 DNS 요청도 늘어난다. 따라서 먼저 가까운 곳에 저장된 답이 있는지 확인한다.

```
브라우저가 저장한 주소 확인
            ↓ 없음
컴퓨터가 저장한 주소 확인
            ↓ 없음
컴퓨터에 직접 설정한 주소 확인
            ↓ 없음
DNS 리졸버에 질문
```

컴퓨터에 직접 설정한 주소의 대표적인 예로 `hosts` 파일이 있다. 이 파일에는 사용자가 도메인 이름과 IP 주소를 직접 연결할 수 있다.

정확한 확인 순서는 운영체제와 브라우저 설정에 따라 달라질 수 있다. 핵심은 **저장된 답이 있으면 외부 DNS에 다시 질문하지 않아도 된다**는 것이다.

### 캐시의 장점

- DNS 주소를 더 빠르게 확인할 수 있다.
- 반복되는 DNS 요청을 줄일 수 있다.
- DNS 서버의 부하를 줄일 수 있다.

---

## 6. TTL

DNS 정보를 캐시에 영원히 저장하면 서버 주소가 변경되어도 이전 주소를 계속 사용할 수 있다. 이를 방지하기 위해 DNS 레코드에는 **TTL**이 설정된다.

TTL은 **Time To Live**의 약자로, DNS 응답을 캐시에 얼마나 오래 저장할지 정하는 시간이다. 일반적으로 초 단위로 설정한다.

예를 들어 TTL이 300초라면 DNS 응답을 최대 5분 동안 저장해 사용한다.

```
주소 확인 → 5분간 저장 → TTL 만료 → 주소 다시 확인
```

### TTL이 긴 경우

- 저장된 정보를 오래 사용하므로 DNS 조회 횟수가 줄어든다.
- DNS 주소를 변경했을 때 이전 정보가 오래 남을 수 있다.

### TTL이 짧은 경우

- DNS 주소 변경이 비교적 빠르게 반영된다.
- DNS 서버에 보내는 요청이 증가한다.

TTL은 무조건 짧거나 길게 설정하기보다 서비스의 변경 가능성과 운영 목적에 따라 정해야 한다.

---

## 7. DNS 리졸버

컴퓨터에 저장된 주소가 없거나 TTL이 끝나면 외부 DNS에 질문해야 한다.

이때 컴퓨터가 여러 DNS 서버를 직접 방문하지 않고 **재귀 DNS 리졸버**에 주소 찾기를 요청한다.

```
사용자
  ↓ www.cotato.com의 IP 주소 요청
DNS 리졸버
  ↓ 여러 DNS 서버에 대신 질문
사용자
  ↓ 최종 IP 주소 수신
```

리졸버는 사용자를 대신해 필요한 DNS 서버에 질문하고 최종 결과를 돌려준다.

리졸버가 이전에 같은 주소를 조회해 캐시에 저장하고 있다면 다른 서버에 질문하지 않고 바로 답할 수도 있다.

일반적으로 인터넷 서비스 제공 업체의 리졸버를 사용하며, Google Public DNS나 Cloudflare의 `1.1.1.1` 같은 공개 리졸버를 사용할 수도 있다.

---

## 8. DNS의 주요 서버

리졸버의 캐시에도 답이 없다면 DNS 계층에 있는 서버의 안내를 받아 주소를 찾는다.

### 루트 네임서버

DNS 조회의 시작점이다. 최종 IP 주소를 직접 알려주는 것이 아니라 `.com`을 담당하는 TLD 네임서버의 위치를 안내한다.

### TLD 네임서버

`.com`, `.org`, `.net` 같은 최상위 도메인을 담당한다. `cotato.com`의 정보를 관리하는 권한 있는 네임서버를 안내한다.

### 권한 있는 네임서버

특정 도메인의 실제 DNS 레코드를 관리한다. 요청한 이름에 해당하는 IP 주소나 CNAME 등의 정보를 제공한다.

| 서버 | 쉽게 표현한 역할 |
| --- | --- |
| 루트 네임서버 | `.com` 담당 서버는 여기 있어 |
| TLD 네임서버 | `cotato.com` 담당 서버는 여기 있어 |
| 권한 있는 네임서버 | 요청한 도메인의 DNS 정보는 이것이야 |

---

## 9. DNS 조회의 전체 과정

리졸버의 캐시에도 답이 없다고 가정하면 다음 순서로 조회한다.

```
1. 사용자 → 리졸버
   www.cotato.com의 IP 주소 요청

2. 리졸버 → 루트 네임서버
   .com 담당 TLD 네임서버 확인

3. 리졸버 → .com TLD 네임서버
   cotato.com의 권한 있는 네임서버 확인

4. 리졸버 → 권한 있는 네임서버
   www.cotato.com의 DNS 레코드 확인

5. 리졸버 → 사용자
   최종 결과 전달 및 캐시 저장
```

실제 조회에서는 중간 결과가 캐시에 저장되어 있을 수 있다. 이 경우 매번 루트 네임서버부터 전체 과정을 반복하지 않고 저장된 정보로 일부 단계를 생략한다.

### DNS의 두 가지 질문 방식

| 방식 | 의미 |
| --- | --- |
| 재귀적 질의 | 최종 답까지 찾아서 알려줘 |
| 반복적 질의 | 답이 없다면 다음에 질문할 서버를 알려줘 |

사용자는 리졸버에 최종 답을 요청한다. 리졸버는 각 DNS 서버가 알려주는 다음 위치를 따라가며 최종 정보를 찾는다.

## 10. DNS 레코드

DNS 레코드는 도메인에 어떤 정보를 연결할지 나타내는 설정이다. 권한 있는 DNS 서버는 이 레코드를 바탕으로 요청에 응답한다.

| 종류 | 역할 | 예시 |
| --- | --- | --- |
| A | 도메인을 IPv4 주소에 연결 | `api.cotato.com` → `203.0.113.10` |
| AAAA | 도메인을 IPv6 주소에 연결 | 도메인 → IPv6 주소 |
| CNAME | 도메인을 다른 도메인 이름에 연결 | `www.cotato.com` → `service.host.com` |
| MX | 이메일을 받을 메일 서버 지정 | 도메인 → 메일 서버 |
| TXT | 인증이나 정책에 사용하는 문자열 저장 | 도메인 소유 확인 |

웹 서비스를 연결할 때는 A와 CNAME 레코드를 자주 사용한다. 이메일 서비스를 구성할 때는 MX와 TXT 레코드도 중요하다.

---

## 11. A 레코드와 CNAME

### A 레코드

A 레코드는 도메인 이름을 IPv4 주소에 직접 연결한다.

```
api.cotato.com → 203.0.113.10
```

`api.cotato.com`을 조회하면 DNS 서버가 IP 주소를 직접 응답한다.

### CNAME 레코드

CNAME은 도메인 이름을 다른 도메인 이름에 연결한다.

```
www.cotato.com → service.host.com → IP 주소
```

`www.cotato.com`을 조회하면 먼저 `service.host.com`이라는 다른 이름을 받는다. 이후 해당 이름의 IP 주소를 추가로 조회한다.

CNAME은 외부 호스팅이나 CDN 서비스에서 제공한 도메인 이름에 사용자 도메인을 연결할 때 활용할 수 있다.

| 레코드 | 연결 대상 |
| --- | --- |
| A | IP 주소 |
| CNAME | 다른 도메인 이름 |

---

## 12. 서브도메인의 활용

서브도메인을 사용하면 하나의 등록 도메인 아래에서 서비스의 목적을 구분할 수 있다.

```
www.cotato.com     사용자 웹사이트
admin.cotato.com   관리자 도구
api.cotato.com     API 서버
static.cotato.com  이미지와 정적 파일
```

각 서브도메인에는 서로 다른 DNS 레코드를 설정할 수 있다. 따라서 같은 `cotato.com` 아래에서도 주소마다 다른 서버나 외부 서비스로 연결할 수 있다.

`www`, `admin`, `api` 같은 이름의 역할이 기술적으로 정해진 것은 아니다. 서비스 운영자가 목적에 맞게 이름과 연결 대상을 정한다.

---

## 13. DNS와 CDN

CDN은 **Content Delivery Network**의 약자로, 여러 지역에 분산된 서버에 콘텐츠를 저장하고 사용자에게 가까운 위치에서 전달하는 시스템이다.

웹사이트의 이미지나 동영상이 멀리 있는 서버에만 저장되어 있다면 사용자와 서버 사이의 물리적 거리가 길어져 응답이 느려질 수 있다.

CDN을 사용하면 여러 지역의 서버에 콘텐츠를 캐시하고, 사용자를 적절한 서버로 연결할 수 있다.

```
서울 사용자 → 가까운 CDN 서버
부산 사용자 → 가까운 CDN 서버
```

DNS와 CDN의 라우팅 기술을 함께 사용하면 사용자에게 지연 시간이 낮은 서버를 안내할 수 있다. 정확한 서버 선택 방식은 CDN 제공 업체와 설정에 따라 달라진다.

---

## 14. DNS 변경의 반영 시간

DNS 레코드의 IP 주소를 변경해도 모든 사용자에게 동시에 새로운 주소가 적용되지는 않는다.

여러 DNS 리졸버에 이전 응답이 TTL 동안 캐시되어 있을 수 있기 때문이다.

```
DNS 주소 변경
   ├─ TTL이 남은 사용자 → 이전 주소 사용
   └─ TTL이 끝난 사용자 → 새 주소 조회
```

기존 캐시의 TTL이 끝나면 리졸버가 새로운 정보를 조회한다. 이 과정을 일반적으로 **DNS 변경 사항이 전파되는 데 시간이 걸린다**고 표현한다.

서비스 주소 변경을 준비할 때는 미리 TTL을 낮춰 이전 정보가 오래 남지 않도록 운영하기도 한다.

---

## 15. DNS 장애

DNS가 올바른 주소를 제공하지 못하면 웹 서버가 정상이어도 사용자는 서비스에 접속하지 못할 수 있다.

### 대표적인 원인

- A 또는 CNAME 레코드의 오타
- 필요한 DNS 레코드의 누락
- 도메인 등록 기간 만료
- 잘못된 네임서버 설정
- DNS 서버나 외부 제공 업체의 장애
- 오래된 DNS 캐시

### 사용자에게 나타나는 현상

- 사이트에 연결할 수 없다는 메시지
- 서버의 IP 주소를 찾을 수 없다는 메시지
- 일부 사용자만 이전 서버로 연결되는 현상
- 특정 서브도메인만 접속되지 않는 현상

DNS 관련 장애를 확인할 때는 웹 서버 상태뿐 아니라 도메인 등록 상태, DNS 레코드, 네임서버 설정과 TTL도 함께 확인해야 한다.
