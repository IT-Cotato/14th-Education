Git에서는 이렇게 각자 기능을 분담해 개발할 수 있는 독립적인 공간인 브랜치를 활용해, 효율적인 협업이 가능하도록 도와줍니다.

### 29페이지 — Git의 차원관리(5)

브랜치가 영어로 ‘가지’를 의미하는 단어잖아요.

나무가 자라면서 여러 갈래로 가지를 뻗어나가듯이, Git에서도 하나의 프로젝트가 여러 갈래로 갈라져 나와 각자만의 버전 이력을 만들어 관리할 수 있습니다.

이 브랜치 덕분에 다양한 작업을 독립적으로 동시에 진행할 수 있고,

각각의 작업이 프로젝트 전체에 영향을 주지 않도록 관리할 수 있습니다.

즉, Git의 기본 기능은 **시간** 흐름에 따라 버전을 기록하는 것이고, 브랜치 기능을 통해 그 흐름을 **여러 갈래**로 나누는 것이라고 할 수 있겠습니다.

### 30페이지 — 분산 버전 관리 시스템이란?

그럼 지금까지 알아본 내용을 바탕으로, 분산 버전 관리 시스템이 무엇인지 정리하고 가겠습니다.

분산 버전 관리 시스템은

모든 개발자가 **코드와 변경이력이 모두 있는 전체 저장소를 각자 로컬에 복제해서 작업하는 구조**를 의미합니다.

즉, 중앙 서버에서만 의존적으로 코드를 관리하지 않는 것이 아니라, 각자 하나씩 완전한 저장소를 가지고 있는 것이죠.

그렇기 때문에 서버에 문제가 생겨도 각자의 로컬 저장소에 버전이 보관되어 있으므로 복구가 쉽게 가능하고, 

여러 개발자가 협업 시에 동일한 코드를 가지고 병렬적으로 작업이 가능하며, 각자의 작업을 병합하는 과정이 유연합니다.

### 31페이지 — GitHub란?

그럼 Git과 GitHub는 무엇이 다를까요?

Git은 앞서 계속 말했듯 VCS, 즉 ‘버전 관리를 도와주는 시스템’이고, GitHub는 Git 저장소를 온라인에 올려 협업할 수 있게 해주는 웹 서비스 플랫폼입니다.

원격 저장소라고도 부르는데요, github는 pull request, Issue, Code Review와 같은 다양한 협업 기능을 제공합니다. 그 외에도 CI/CD 기능과, 테스트 및 배포 등 자동화 워크 플로우 기능도 제공하죠. 

그리고 웹에서 바로 코드를 확인하는 것도 가능합니다.

Git으로 관리한 코드를 인터넷에 올려서 협업하는 공간이라고 정리할 수 있을 것 같습니다.

### 32페이지 — Git 구조(1)

이제 Git의 내부 구조에 대해서 조금 더 자세히 보겠습니다.

다들 잘 듣고 계시죠? ㅎㅎ
얼마 안 남았으니 모두 힘내서 들어주세요!

git은 다음과 같은 공간에서 각 파일들의 상태를 관리하는데요.

1. working directory: 내 컴퓨터에서 실제로 파일을 만들고, 수정하는 공간입니다. 새로 만든 파일(untracked)도 있고, 기존 내용을 수정한 변경 파일(modified)도 있을 수 있습니다.
2. staging area: 커밋하기 이전에, 수정된 파일을 저장하는 장소라고 할 수 있습니다. 
3. local repository: 커밋된 파일들이 보관되는 저장소입니다.

여기까지는 내 노트북에 한정해서 자유롭게 공간을 넘나들 수 있었다면,

1. remote repository: 원격 저장소, 즉 모든 작업자의 push된 코드를 모아두는 저장소입니다.

### 33페이지 — Git 구조(2)

프로젝트에 있는 파일들이 어떻게 각 영역에 저장되는지, 알기 쉽게 나타낸다면 화면에 있는 그림처럼 표현할 수 있습니다.

먼저 git add를 통해 작업 디렉토리에 있는 파일들을 스테이징 영역에 올립니다. 스테이징 영역에 있는 파일들은 다음 커밋에 포함되는데요.

그 뒤, git commit을 하면 staging area에 있는 파일들을 하나의 버전(커밋)으로 저장합니다. 변경 이력이 Git에 저장되는 거죠.

이 상태에서 git push 명령어를 입력하면, 로컬 저장소의 커밋을 원격 저장소(GitHub)로 업로드하게 됩니다.

반대로 원격 저장소의 최신 변경 내용을 가져와 작업 디렉토리에 반영할 때는 git pull 명령어를 사용합니다.

### 34페이지 — Git 필수 명령어(1)

앞에서 살펴본 것 외에도, 협업 시에 필수로 사용하는 명령어들은 화면에 있는 것과 같습니다.

다른 것들은 이미 다 살펴본 명령어이고, git clone과 git merge만 새롭게 나와 있는데.

먼저 git clone은 원격 저장소에 이미 존재하는 프로젝트를 그대로 내려받을 때 사용하는 명령어이고

git merge는 다른 브랜치의 변경 내용을 현재 브랜치에 합치는 명령어 입니다.

### 35페이지 — Git 필수 명령어(2)

그래서 이러한 명령어들을 사용하게 되는 기본 플로우는 이렇습니다.

깃허브에 있는 레포지토리를 clone 해오고, 가장 최신 코드를 pull 하며, 작업을 진행합니다. 

그리고 이 작업한 파일들을 add 명령어로 staging area에 올리고, 

commit 명령어를 통해 staging area에 있던 파일들을 하나의 버전, 즉 커밋으로 저장합니다.

그리고 다른 팀원들과 공유할 수 있도록 push 명령어를 통해 원격 저장소에 업로드합니다.

이때, push를 하기 전에 꼭 pull, 즉 원격 저장소의 최신 변경 내용을 로컬에 반영하도록 하는 작업이 중요한데요.

파일을 최신 버전으로 동기화하고, 다른 팀원의 작업 내용과의 충돌(conflict)을 방지하기 위함입니다.
